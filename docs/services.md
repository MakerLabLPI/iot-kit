# Services and web UIs

What runs on the Pi, how it is managed, and the web tools available on the kit LAN.

From the host network (WAN side) only SSH answers. The Pi does not answer
ping or `iot-kit.local` there: use its IP, or connect through the kit's own
LAN. To allow `iot-kit.local` on the WAN side, uncomment the mDNS line in
`configs/nftables/nftables.conf` and re-run `scripts/phase3-firewall.sh`.

# What runs where

| Service | How | At boot |
|---|---|---|
| Interfaces, NAT, firewall | native (NetworkManager, nftables) | yes |
| DHCP + DNS, NTP | native (dnsmasq, chrony) | yes |
| Cockpit | native | yes, on demand (socket) |
| MQTT broker | Docker (`broker/`) | yes |
| Node-RED, MQTTX Web, topic monitor, presence, LED strip | Docker (`tools/`) | yes |
| Exercise services | Docker (`exercises/ex_*/`) | once started by hand |
| UniFi controller + MongoDB | Docker (`unifi/`), host networking | no, `unifi-up.sh` |

The broker, the tools and the exercises share one Docker network, `iot-kit`
(bridge `br-kit`, created by `scripts/phase4-mosquitto.sh`), and publish
their ports: `docker ps` shows who listens where, containers reach the
broker as `mosquitto` (or `broker.lan`), and the firewall lets the LAN reach
every published port. Only UniFi (L2 discovery of the AP) and the presence
scanner (ARP on `eth0`) keep host networking.

`tools/presence/` tells who is on the LAN: every 5 s it pings every DHCP
lease (which forces an ARP exchange, even with devices that ignore ping),
reads the kernel's neighbour table, and publishes on MQTT:
`bme/s04/net/present` (retained: `{"count", "devices": [{ip, mac, name}]}`),
`bme/s04/net/joined` and `bme/s04/net/left` (one message each, a device is
"left" after 3 silent sweeps). `name` is the DHCP hostname (`esp32-65E86C`).
Check: `mosquitto_sub -h broker.lan -t 'bme/s04/net/#' -v`. dnsmasq also
publishes every lease on `bme/s04/net/dhcp` the moment it is given
(`configs/dnsmasq/dhcp-event`): that is the instant "joined the WiFi".

`tools/leds/` drives a 13-LED NeoPixel strip plugged on the Pi, from the
broker only:

| LEDs | Shows | Source |
|---|---|---|
| 0 | power: green, always on | the service runs |
| 1-2 | MQTT: green flash = a client connected, red = disconnected, orange = every message | `$SYS/broker/clients/connected` (refreshed every second), `#` |
| 3-4 | WiFi: green flash = a device joined, red flash = one left | `bme/s04/net/dhcp` (dnsmasq hook), `bme/s04/net/left` (presence) |
| 5-12 | free, set by anyone | `iot-kit/leds/0` ... `iot-kit/leds/7`, `iot-kit/leds/all` |

LED numbers are counted from the far end of the strip (`REVERSE: "1"` in
`tools/docker-compose.yml`; `"0"` counts from the connector). The free LEDs take a colour as payload, RGB or hex: `255,128,0` (also
`rgb(255,128,0)`) or `#ff8000` (also `ff8000`, `#f80`); off is `0,0,0`.
Publish retained to keep it across a restart:
`mosquitto_pub -h broker.lan -t iot-kit/leds/3 -m '#0000ff'`. Connect and
disconnect flashes queue up, one per client; a message blip never hides
them. `QUIET_TOPICS` lists topic prefixes that should not blip.

Wiring (WS2812, 5 V): data in on **GPIO 10** (pin 19, `LED_PIN`), GND on
pin 6, 5 V from pin 2 or 4 **through a diode** (1N4007): at ~4.3 V the
first pixel reads the Pi's 3.3 V data cleanly (at 5 V its threshold is
3.5 V, a level shifter does the same job). `BRIGHTNESS` in
`tools/docker-compose.yml`. The signal is generated by the PIO of the
Pi 5's RP1 chip through Adafruit's `Adafruit-Blinka-Raspberry-Pi5-Neopixel`
(`/dev/pio0`): the classic `rpi_ws281x` does not run on a Pi 5. Hardware
tests, with the service stopped: `docker compose run --rm leds python3
/leds.py solid` (or `rainbow`). A strip that stops after N pixels with
both has a dead pixel or a broken joint there. With `CONSOLE: "1"` the strip is also drawn in
`docker logs leds`, which is how to see it before it is wired.

Everything that can run in a container does. What stays native is the
network itself (a container cannot start without it) and Cockpit, which
manages the host. So the WiFi, DHCP and DNS come up even if Docker does
not; the broker and the web UIs need Docker.

Each stack is handled with `docker compose`, for example:

```sh
cd ~/iot-kit/broker
docker compose ps
docker compose logs -f
docker compose restart
```

`docker` works without `sudo` because `scripts/install-docker.sh` puts the
user who ran the setup in the `docker` group (log out and back in once after
the first setup). That group is equivalent to root on the Pi. The UniFi
scripts still ask for `sudo`: their settings are in `/etc/iot-kit/unifi.env`,
which only root can read.

# Web UIs

All of them are reachable from the kit LAN only. From the host network use
an SSH tunnel, as for the UniFi controller.

## Node-RED: dashboards

- `http://iot-kit.lan:1880/dashboard` is open to everyone. The starter flow
  shows the number of connected clients, the message rate and the last value
  of every topic: a student sees their ESP32 appear there.
- `http://iot-kit.lan:1880` is the editor. Everyone can look at the flows,
  only `admin` can change them. Password: `sudo cat
  /etc/iot-kit/nodered-admin-password`. To change it, edit that file and run
  `sudo ~/iot-kit/scripts/phase7-webui.sh`.
- Whoever can edit flows can run code in the container. Give the admin
  password to students only if that is what the workshop is about.
- Installing more nodes from the editor needs the internet uplink.
- `tools/nodered/flows.json` is only the starter: it is copied once, what
  you build afterwards lives in `/var/lib/iot-kit/nodered/` and is never
  overwritten.

## MQTTX Web: MQTT client in the browser

`http://iot-kit.lan:8090`, then "New connection" with:

| Field | Value |
|---|---|
| Host | `ws://` `broker.lan` |
| Port | `9001` |
| Path | `/mqtt` |
| Username / password | empty |

Connections are stored in the browser, so everyone has their own. A browser
can only speak MQTT over WebSockets, hence port 9001 and not 1883.

## Cockpit: the router itself

`https://iot-kit.lan:9090`, login with the `pi` account. Traffic graphs per
interface, state and logs of every service, a terminal. It is an admin tool:
its Networking page can change `eth0` and cut the kit's LAN.

Anyone on the kit WiFi who knows the `pi` password gets a root terminal
there (and over SSH): **change the default password** before a workshop.
